1. Introduction

1.1 Purpose

This SRS defines the requirements of the implemented TODA President Control Panel, a local-first software system used by one TODA President/operator to manage driver records, fares, complaint intake (via Google Forms CSV import), and audit history.

1.2 Product scope

The product is designed for a single local deployment and a single operational user role (President). It is not a cloud-hosted, multi-tenant, passenger-account, booking, dispatching, or payment platform.

1.3 Stakeholders and users

  • Primary operational user: TODA President (logs in to the control panel, performs all management actions).
  • Informational stakeholders: TODA officers and municipal stakeholders reviewing records/reports generated by the President.
  • External participants (not control-panel users): passengers/commuters who scan a printed driver QR code and submit complaints through an external Google Form.

2. System context and architecture

2.1 Implementation architecture

  • Frontend: React + Vite (entry in src/main.tsx, app in src/App.tsx).
  • Backend API: Node.js + Express (server.js).
  • Database: local MySQL database (toda).
  • Local file storage: driver photos in uploads/driver-photos/, temporary CSV files in temp/.

2.2 Deployment and runtime mode

  • Normal packaged/local startup: start-toda.bat serves the frontend from the API host at http://localhost:5000.
  • Development mode: API commonly at http://127.0.0.1:5000 and Vite dev frontend at http://localhost:8443.
  • System operation is local-first; previously imported records remain available locally without continuous internet.
  • Internet access is still required when commuters submit complaints through Google Forms.

3. In-scope and out-of-scope definition

3.1 In scope

  • President login, logout, session check, and password change.
  • Driver/tricycle registry: add, list, edit, activate/inactivate, archive.
  • Driver profile data: driver name, body number, plate number, phone, address, license number, member-since date, optional photo.
  • Driver-specific QR code generation in-browser, opening a shared Google complaint form with prefilled body number.
  • Printable QR sheets for filtered driver sets.
  • Fare reference viewing and editing.
  • Google Forms CSV complaint import with header mapping, preview/validation, duplicate detection, and local complaint tracking.
  • Complaint resolution status toggling.
  • Audit Log viewing.
  • Backup/restore procedures and local operational scripts.

3.2 Explicitly out of scope (excluded features)

  • Public commuter or passenger application accounts.
  • Online/public driver lookup portal.
  • Automated municipal approval workflow.
  • Online payments, e-wallets, receipts, driver revenue reports, billing workflows.
  • Live Google Forms API integration (import is CSV file based).
  • Cloud database hosting or cloud multi-tenant architecture.
  • GPS/live tracking, booking, dispatching, SMS/email notification pipeline.
  • Multiple organizations/roles/tenant switching.
  • Non-tricycle vehicle categories (cars, jeepneys, buses, etc.).
  • Autonomous synchronization between separate computers.

8. Constraints, assumptions, and open project decisions

8.1 Constraints

  • Single local TODA operator model.
  • Local MySQL availability is required for authenticated operations.
  • No automatic synchronization between separate computers.
  • Google Forms complaint submission depends on internet access by commuter devices.

8.2 Assumptions

  • President credentials are controlled by the organization and stored securely outside project files.
  • Operator follows backup procedures for both SQL backups and photo folder copies.
  • Authorized host machine is physically and administratively controlled by TODA management.

8.3 Open items requiring project decisions

  • Official municipality name and final approved fare values.
  • Final body-number format policy and required client field list.
  • Complaint/audit retention period and export requirements.
  • Need for printable driver ID cards beyond QR sheets.
  • Formal password-reset process for production handoff.

9. Implementation status

9.1 Completed capabilities

  • Local React/Vite frontend and Node.js/Express backend.
  • MySQL-backed sessions and local-first data management.
  • President login/logout/password change with inactivity timeout and login throttling.
  • Driver registry CRUD-like management (add/view/edit/activate-inactivate/archive) with photos.
  • Local QR generation and printable QR sheets.
  • Fare reference panel and persistence.
  • Google Forms CSV complaint import with duplicate detection and complaint status updates.
  • Audit logging and review route.
  • Backup/restore operational scripts and documented local deployment flow.

9.2 Pending/recommended acceptance work

  • Run full authenticated test suite on a machine with authorized real test credentials.
  • Perform end-to-end browser acceptance pass: login, registry operations, photo reload, QR scan, CSV import, complaint resolution, password change, audit review, and restore rehearsal.

  1. Verify each FR and NFR through route-level tests, controlled manual UI tests, and local DB/file inspection where applicable.
  2. Treat unsupported features in Section 3.2 as explicit non-requirements for this release baseline.
  3. Use this SRS as baseline documentation for local client deployment and future maintenance increments.
